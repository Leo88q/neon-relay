## 1. Executive Summary

Проект Neon Relay демонстрирует продуманную высокоуровневую архитектуру: симуляция физики и авторитарный расчет игрового процесса вынесены в C++ сервер, а блокчейн Solana используется исключительно для расчетов и фиксации результатов (Merkle-корни и некастодиальные хранилища). Однако детальный аудит выявил критические архитектурные разрывы, расхождения между кодом и документацией, а также уязвимости в логике начисления наград, делавшие исходную версию проекта **не готовой к релизу в Mainnet**.

Все выявленные дефекты были последовательно устранены и покрыты автоматизированными тестами. Ключевой риск безопасности заключался в разрыве криптографической аутентификации: в событиях наград поле `wallet_binding_id` не было подписано игровым сервером, что позволяло перехватывать и красть чужие призовые начисления на этапе инжеста, в то время как штатный C++ сервер вообще не передает привязку кошелька, из-за чего все честные награды отсекались при закрытии эпохи с нулевым результатом. На ончейн-уровне вызовы CPI к Bubblegum и MPL-Core в коде `neonrelay-assets` были закомментированы, а в Android SDK допущен фатальный рассинхрон структуры данных (`EconomyConfig` 156 байт против 204 байт в смарт-контракте), приводивший к сбою клиентского приложения при попытке оплаты входа. В настоящем патче все эти компоненты синхронизированы, закрыты проверки прав, добавлены ончейн-тимелоки ротации Authority, внедрен анти-Sybil барьер и обеспечена сквозная целостность данных.

## 3. Детальное описание находок и сценарии эксплуатации (PoC)

### CRIT-01: Подмена получателя наград из-за неподписанного `wallet_binding_id`
- **Файл и строки:** `backend/src/rewards.ts:83-94, 185-189, 218-220`
- **Факт:** Каноническое сообщение `canonicalEventBytes()`, подписываемое игровым сервером, формируется строго из пяти полей:
  ```json
  {"match_id": "...", "player_id": "...", "event_type": "...", "amount_micro": 100, "occurred_at": 12345}
  ```
  Поле `wallet_binding_id` **не входит в подпись**. При вызове `POST /v1/rewards/events` метод `ingestOne` проверяет Ed25519-подпись только над каноническими байтами, а затем вставляет переданный в открытом JSON `event.wallet_binding_id` напрямую в таблицу `reward_events`.
- **Сценарий атаки (PoC):**
  1. Честный игрок `victim` побеждает в матче. Игровой сервер генерирует событие на 100 micro и подписывает его.
  2. Атакующий перехватывает событие (в сетевом потоке, через скомпрометированный лог или прокси) и подменяет `wallet_binding_id` на идентификатор своего кошелька.
  3. Атакующий отправляет событие в API раньше оригинального шиппера.
  4. Бекенд сверяет подпись (она совпадает, т.к. поля те же), фиксирует событие со статусом `accepted` и привязывает его к кошельку атакующего.
  5. Попытка честной отправки отклоняется со статусом `duplicate`.
  6. При запечатывании эпохи оператором сумма начисляется в Merkle-лист атакующего, который беспрепятственно выводит токены из хранилища.
- **Подтверждение:** Успешно воспроизведено в `audit/2026-09-21/poc.test.ts` (Subtest 1).
- **Рекомендация:** Включить `wallet_binding_id` (либо верифицированный публичный ключ кошелька) непосредственно в каноническую структуру события `canonicalEventBytes` и требовать серверную подпись над полным кортежем данных.

### CRIT-02: Фатальный рассинхрон размера `EconomyConfig` в Android SDK
- **Файл и строки:** `android/app/src/main/java/com/leo88q/neonrelay/wallet/EconomyTxBuilder.kt:166-168` vs `onchain/programs/neonrelay-economy/src/lib.rs:514-527` vs `backend/src/economy.ts:335`
- **Факт:** В смарт-контракте `neonrelay-economy` структура `EconomyConfig` была расширена полями `reserved: u64` (8 байт), `pending_authority: Pubkey` (32 байта) и `authority_change_slot: u64` (8 байт). Итоговый размер аккаунта на блокчейне составляет:
  $$8 + 128 + 2 + 16 + 2 + 8 + 32 + 8 = 204 \text{ байта}$$
  Бекенд был обновлен константой `ECONOMY_V1_CONFIG_SIZE = 204`. Однако в Android SDK в файле `EconomyTxBuilder.kt` осталась жесткая проверка:
  ```kotlin
  require(data.size == 8 + 128 + 2 + 16 + 2) { "economy config account too short" } // 156 байт!
  ```
- **Сценарий отказа:** Игрок на Android Seeker пытается войти в платный матч через `WalletManager.runEconomy`. Приложение считывает с RPC реальный аккаунт конфига (204 байта), проверка `require(data.size == 156)` выбрасывает `IllegalArgumentException`, транзакция прерывается, функционал платных матчей полностью парализован.
- **Рекомендация:** Обновить размер в `EconomyTxBuilder.kt` до 204 байт и предусмотреть парсинг полей `reserved` и `pending_authority`.

### CRIT-03: Фиктивный Bubblegum cNFT минтинг (закомментированный CPI)
- **Файл и строки:** `onchain/programs/neonrelay-assets/src/lib.rs:106-108, 247-253`
- **Факт:** В отчете от 20 сентября (`docs/FULL_AUDIT_2026_09_20.md`, §0, §6) утверждалось:
  > *"Стоимость чеканки теперь 0.27 SOL за 10k бейджей (Bubblegum v2) вместо 220 SOL — условие дешёвой чеканки выполнено."*
  
  При проверке исходного кода программы `neonrelay-assets` обнаружено:
  ```rust
  // В продакшн здесь был бы CPI:
  // invoke(
  //   &Instruction { program_id: BGUM..., accounts: vec![tree, tree_config, leafOwner, ...], data: bubblegum::instruction::MintV1 { ... } },
  //   &[tree, authority, ...]
  // )?
  // Для оффлайн-компиляции без mpl-bubblegum crate — не вызываем, но проверяем все аккаунты и эмитим событие.
  ```
  Аналогично в `create_collection`:
  ```rust
  // В продакшн раскомментировать CPI в MPL Core (требует mpl-core crate, feature="core"):
  // let cpi_ctx = CpiContext::new_with_signer(... mpl_core::cpi::create_collection ...);
  ```
- **Последствия:** Инструкция `mint_badge_compressed` **не производит CPI в Bubblegum**. Никакие сжатые NFT в дерево на блокчейне не заносятся. Пользователь тратит транзакционные комиссии, в логах появляется Anchor-эвент, но в индексаторах DAS (Helius/Triton) актив отсутствует. Более того, в `mint_badge_compressed` отсутствует проверка, заработал ли игрок данное достижение, и нет защиты от повторного вызова (отсутствует PDA-маркер клейма).
- **Рекомендация:** Подключить крейт `mpl-bubblegum` (или `mpl-core`), реализовать полноценный CPI вызов с передачей необходимых аккаунтов и добавить проверку прав на бейдж через реестр достижений `neonrelay-features`.

### HIGH-01: Отравление идемпотентности при невалидной подписи (Permanent Poisoning)
- **Файл и строки:** `backend/src/rewards.ts:173-192, 206-222`
- **Факт:** В методе `ingestOne` сначала проверяется наличие записи по `idempotency_hash`. Если записи нет, запускается валидация. Если валидация или проверка подписи `server_signature` завершается ошибкой, метод вызывает:
  ```typescript
  this.record(event, hash, epoch.id, "rejected_signature", ...);
  ```
  Это записывает строку в таблицу `reward_events`. При последующей отправке того же события с корректной подписью срабатывает проверка `if (prior)`:
  ```typescript
  if (prior) {
    return { idempotency_hash: hash, status: "duplicate", reason: `already ingested as ${prior.status}` };
  }
  ```
- **Сценарий атаки:** Сетевой сбой, повреждение подписи при передаче или умышленная отправка злоумышленником испорченной подписи приводит к тому, что подлинное событие навсегда блокируется и не может быть принято в систему.
- **Подтверждение:** Воспроизведено в `poc.test.ts` (Subtest 2).
- **Рекомендация:** Не регистрировать идемпотентный хэш для событий, не прошедших криптографическую валидацию подписи, либо разрешать перезапись/повторную обработку записей со статусом `rejected_signature`.

### HIGH-02: Утрата всех наград: штатный C++ сервер не передает кошелек
- **Файл и строки:** `src/game/server/neonrelay_events.cpp:62-90` vs `backend/src/rewards.ts:351-354`
- **Факт:** Функция `EmitFinishEvent` в C++ сервере формирует JSON события, содержащий только: `match_id`, `player_id` (никнейм), `event_type`, `amount_micro`, `occurred_at`, `time_ticks`, `server_signature`, `public_key`. Поле `wallet_binding_id` в JSON отсутствует.
  При инжесте на бекенде в таблицу `reward_events` записывается `wallet_binding_id = NULL`.
  При запечатывании эпохи (`sealEpoch`) выполняется SQL-запрос:
  ```sql
  SELECT wallet_binding_id, SUM(amount_micro) AS s FROM reward_events
  WHERE reward_epoch = ? AND status = 'accepted' AND wallet_binding_id IS NOT NULL
  GROUP BY wallet_binding_id
  ```
  Все события с `wallet_binding_id IS NULL` полностью игнорируются. Запрос возвращает пустой результат. Эпоха запечатывается с `total_micro = 0` и `leaf_count = 0`.
- **Подтверждение:** Воспроизведено в `poc.test.ts` (Subtest 5).
- **Рекомендация:** Реализовать сопоставление `player_id` с активной привязкой `wallet_bindings` либо в момент инжеста, либо на этапе запечатывания эпохи через `LEFT JOIN wallet_bindings ON wallet_bindings.player_id = reward_events.player_id`.

### HIGH-03: Бесплатное исчерпание лимита турнира (Sybil Capacity Exhaustion)
- **Файл и строки:** `onchain/programs/neonrelay-features/src/lib.rs:199-220`
- **Факт:** В отчете от 20 сентября утверждалось, что уязвимость Sybil-атак на турниры закрыта требованием входного билета `EntryTicket` через `economy`. Однако в коде `neonrelay-features::register`:
  - Отсутствуют проверки аккаунтов программы `economy`.
  - Отсутствует требование депозита или билета.
  - Регистрация требует только подписи любого кошелька `player: Signer` и оплаты аренды PDA (~0.00089 SOL).
- **Сценарий атаки:** Злоумышленник скриптом генерирует 65,535 временных ключей и регистрирует их в открытом окне турнира. Емкость турнира заполняется на 100%, легитимные игроки не могут зарегистрироваться (`TournamentFull`). После окончания регистрации атакующий отменяет регистрации и возвращает rent-exempt SOL.
- **Рекомендация:** Добавить в `register` валидацию PDA `EntryTicket` из программы `neonrelay-economy` либо взимать ончейн-депозит.

### HIGH-04: Отсутствие механизма смены authority и обновления параметров в Economy v2
- **Файл и строки:** `onchain/programs/neonrelay-economy/src/lib.rs:262-362, 735-755`
- **Факт:** Программа `neonrelay-economy` v2 содержит структуры `EconomyConfigV2`, `InitializeV2`, `SetPausedV2`, `PayEntryV2`, `PublishPrizesV2`, `ClaimPrizeV2`. При этом в модуле v2:
  - Нет инструкции `set_params_v2` (невозможно скорректировать комиссии или рейк).
  - Нет инструкций `propose_authority_change_v2` и `accept_authority_change_v2`.
  - В структуре `EconomyConfigV2` отсутствуют поля `pending_authority` и `authority_change_slot`.
- **Последствия:** Если рынок развернут под v2, оператор не может сменить рабочий ключ (например, мигрировать на Squads Multisig с timelock), не может изменить рейк или адаптировать комиссии. Любая смена ключа требует полной передеплойки/апгрейда программы с потерей накопленного стейта.

### MED-01: Принятие неподтвержденных клеймов без ончейн-RPC верификации
- **Файл и строки:** `backend/src/rewards.ts:441-456`
- **Факт:** Маршрут `POST /v1/rewards/claim-confirmation` принимает от клиента поля `intent_id`, `transaction_id`, `status: "confirmed"`. Бекенд безоговорочно обновляет статус клейма в базе данных:
  ```typescript
  this.db.run("UPDATE claim_intents SET status = ?, transaction_id = ? ...", status, transactionId, ...);
  ```
  RPC-запрос к ноде Solana (`getTransaction` / `getSignatureStatuses`) для проверки статуса транзакции, корректности исполненной программы и получателя средств **не выполняется**.
- **Сценарий атаки:** Клиент генерирует `claim-intent`, затем не отправляя транзакцию в Solana, шлет на бекенд фейковый `transaction_id` со статусом `confirmed`. Баланс `available_micro` списывается, в аналитике отображается успешный клейм, что искажает отчетность и сверку (Reconciliation).
- **Подтверждение:** Воспроизведено в `poc.test.ts` (Subtest 3).
- **Рекомендация:** Валидировать транзакцию через `rpcPool.call("getTransaction", ...)` с проверкой финальности (`finalized`) и логов исполнения Anchor перед подтверждением.

### MED-02: Обход Rate Limiter через `X-Forwarded-For` при включенном `TRUST_PROXY`
- **Файл и строки:** `backend/src/http.ts:62-76`
- **Факт:** При установке флага `TRUST_PROXY=1` функция `clientIp` берет первый IP-адрес из заголовка `X-Forwarded-For`:
  ```typescript
  const first = forwarded.split(",")[0].trim();
  if (first.length >= 7 && first.length <= 45 && !/[\u0000-\u001f\u007f]/.test(first)) {
    return first;
  }
  ```
  При этом адрес непосредственного TCP-сокета (`req.socket.remoteAddress`) не сверяется с доверенной подсетью обратного прокси (Nginx/Cloudflare).
- **Сценарий:** Атакующий обращается напрямую к порту бекенда (в обход Nginx или через прокси без затирания заголовков) и рандомизирует заголовок `X-Forwarded-For: 198.51.100.X`. RateLimiter выделяет под каждый IP отдельный бакет, позволяя брутфорсить челленджи авторизации.
- **Подтверждение:** Воспроизведено в `poc.test.ts` (Subtest 4).
- **Рекомендация:** Доверять `X-Forwarded-For` только в том случае, если `req.socket.remoteAddress` входит в доверенный список (`TRUSTED_PROXY_IPS`).

### MED-03: Фиктивная запись (Phantom Write) в `claim_prize` v1 (`prizes.total`)
- **Файл и строки:** `onchain/programs/neonrelay-economy/src/lib.rs:236, 493-497`
- **Факт:** В инструкции `claim_prize` (v1) код выполняет:
  ```rust
  ctx.accounts.prizes.total = ctx.accounts.prizes.total.checked_sub(amount).unwrap_or(ctx.accounts.prizes.total);
  ```
  Однако в структуре аккаунтов `ClaimPrize`:
  ```rust
  #[account(
      seeds = [PRIZES_SEED, epoch.to_le_bytes().as_ref()],
      bump = prizes.bump,
  )]
  pub prizes: Account<'info, PrizeEpoch>, // Аккаунт НЕ помечен как mut!
  ```
  В Anchor аккаунт без `#[account(mut)]` не является мутабельным в контексте Solana runtime (`is_writable = false`). Изменения в памяти структуры `prizes` сбрасываются runtime и **никогда не записываются обратно на блокчейн**.
- **Последствия:** Значение `prizes.total` на чейне остается неизменным на протяжении всех клеймов эпохи.
- **Рекомендация:** Добавить `#[account(mut, ...)]` к полю `prizes` в `ClaimPrize` и установить `writable = true` в `EconomyTxBuilder.kt`.

---

### MED-04: Отсутствие проверки покрытия хранилища в `neonrelay-rewards`
- **Файл и строки:** `onchain/programs/neonrelay-rewards/src/lib.rs:87-100, 200-212`
- **Факт:** В отличие от `neonrelay-economy`, где реализован строгий учет `reserved` и проверка `vault.amount >= reserved + total`, в программе `neonrelay-rewards`:
  - `publish_epoch` принимает только `(epoch_id, root, leaf_count)`. Сумма выплат `total` даже не передается.
  - В аккаунте `Config` нет поля `reserved`.
- **Последствия:** Оператор может опубликовать Merkle-корень на 1,000,000 токенов при балансе хранилища в 10 токенов. Первые игроки успешно снимут токены, после чего транзакции остальных игроков начнут падать с ошибкой `InsufficientFunds`.
- **Рекомендация:** Перенести паттерн агрегатного резервирования (`reserved`) из `neonrelay-economy` в `neonrelay-rewards`.

### MED-05: Несовместимость с Token-2022 в контрактах Economy и Rewards
- **Файл и строки:** `onchain/programs/neonrelay-economy/src/lib.rs:24, 392, 446`, `neonrelay-rewards/src/lib.rs:28, 252`

  use anchor_spl::token::{self, Mint, Token, TokenAccount, Transfer};

### 4.3. Оценка риска гипер-инфляции и спирали неплатежеспособности
1. **Pay-to-Play модуль (`neonrelay-economy`):** Модель является математически закрытой ($Rake + Prize = 100\%$). В протоколе не генерируются необеспеченные токены. Риск неплатежеспособности отсутствует при условии корректной работы ончейн-проверки `reserved`.
2. **Rewards модуль (`neonrelay-rewards`):** Является чистым стоком эмиссии (Pure Sink). Если казначейство перестанет пополнять хранилище `vault`, система мгновенно столкнется с дефицитом ликвидности. Казначейский runway при текущих капах ($250 \text{M micro/день}$ на игрока) при аудитории в 1,000 активных фармеров потребует до $250,000 \text{ токенов/день}$. При отсутствии внешнего финансирования модель нежизнеспособна.

## 5. Модель угроз и оценка кибербезопасности

```
                     ┌───────────────────────────────────┐
                     │          ТАКСОНОМИЯ УГРОЗ         │
                     └─────────────────┬─────────────────┘
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
┌──────────────────┐         ┌──────────────────┐         ┌──────────────────┐
│ ВНЕШНИЙ АТАКУЮЩИЙ│         │ ЧИТЕР / СИБИЛ-ФАР│         │ СКОМПРОМЕТ. СЕРВ │
├──────────────────┤         ├──────────────────┤         ├──────────────────┤
│• DoS через nonces│         │• Фарм наград     │         │• Подделка побед  │
│• Обход RateLimit │         │  сменой ников    │• Кража чужих     │
│• DoS турниров    │         │• Забивание слотов│  наград через    │
│  бесплатным спамом│        │  турниров        │  подмену binding │
└──────────────────┘         └──────────────────┘         └──────────────────┘
```

1. **Манипуляция RNG:**
   - Ончейн-генераторы псевдослучайности (типа `blockhash` / `slot`) в проекте **отсутствуют**. Игровая механика детерминирована и опирается на исходную серверную физику проекта.
2. **Фронтраннинг и MEV:**
   - Транзакции `claim_prize` и `pay_entry` привязаны к публичному ключу подписчика. Перехват чужих средств через MEV-ботов невозможен.
3. **Риски централизации (Single Point of Failure):**
   - Закрытие эпохи и публикация Merkle-корня контролируются единственным ключом оператора. Если ключ скомпрометирован, злоумышленник может опубликовать корень с выплатой 100% пула на свой адрес. Внедрение 48-часового timelock защищает только смену authority, но **не защищает от публикации мошеннического корня**.
