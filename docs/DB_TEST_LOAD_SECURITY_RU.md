## 1. Базы данных: что и как пишет

### 1.1 Бэкенд (основная БД «всего») — SQLite, append-only

`backend/src/db.ts` — `node:sqlite`, режим **WAL**, `foreign_keys=ON`,
форвард-only миграции (`schema_migrations`, отката по дизайну нет). 11 миграций
→ 25+ таблиц:

| Слой | Таблицы | Что фиксирует |
| --- | --- | --- |
| wallet auth | `wallet_bindings`, `auth_nonces`, `sessions` | привязки кошельков, одноразовые nonce, сессии (хранятся только SHA-256 хэши токенов) |
| reward ledger | `reward_events`, `reward_epochs`, `reward_leaves`, `claim_intents` | каждое начисление, эпохи, Merkle-листья, намерения к клеймам |
| экономика v1 | `economy_epochs`, `economy_matches` | эпохи, матч-результаты |
| экономика v2 | `economy_v2_epochs`, `economy_v2_intents` | **SQL-триггеры запрещают изменение/удаление строк**; только OPEN → SEALED (см. `docs/ECONOMY_V2_LEDGER.md`) |
| игровой контур | `game_identity_*`, `game_accounts`, `game_pairings`, `game_events` | identity-челленджи, пейринг «аккаунт-игра», игровые события |
| админ-плоскость | `admin_proposals`, `admin_audit` | каждое действие оператора; изменения — через propose/accept |
| операции | `reconcile_snapshots`, `treasury_snapshots`, `watchtower_events`, `watchtower_identity_links` | снапшоты сверок, телеметрия Watchtower |
| анти-сибил | индексы `0010` | один активный кошелёк → один player id (fail-closed при дублях) |
| память агента | `watchtower_events.memory_mac` (`0011`) | **HMAC-SHA256 на каждую строку** памяти, читаемой ИИ |

«Записывает всё» в смысле аудита: append-only слои (reward_events, экономика v2
с триггерами, admin_audit, watchtower_events с MAC) + **on-chain корень**:
запечённая эпоха публикуется Merkle-корнем отдельным авторитом — это внешний
по отношению к БД неизменяемый журнал.

### 1.2 Игровой сервер — SQLite (или MySQL), плюс файловые журналы

* `sv_sqlite_file` (дефолт `neonrelay-server.sqlite`): таблицы `*_race`,
  `*_teamrace`, `*_maps`, `*_saves`, `*_points` (`src/engine/server/databases/connection.cpp`);
  опционально MySQL (`sv_use_sql`; слой импорта рекордов апстрим-движка).
* **teehistorian** (`sv_tee_historian`): полный журнал игровых данных матча на
  диск («complete gameplay data», предупреждение о месте в конфиге).
* Демо-записи сервера/клиентов (запись/воспроизведение в smoke-тесте).
* Клиент: кэш `server_pings` (SQLite) — не игровая БД.

### 2.3 Нагрузочные тесты — **нет** (честный пробел)

В репозитории нет ни k6/locust/jmeter-сьютов, ни ботового прогона сервера под
N игроками, ни soak-тестов. `docs/BENCHMARKING.md` — только ссылка на
Phoronix-бенчмарк апстрима. Единственные «приближения»: smoke-тест с 2 клиентами
(`integration_test.py`), нативные тесты физики и синтаксис-пробы.

### 2.4 Мутационные тесты — **нет**

Ни Stryker, ни PITest, ни mutatest, ни «mutant»-инфраструктуры нет (проверено
грепом по дереву). Ближайшие функциональные эквиваленты, которые есть:

* self-test'ы сканеров (`check_secrets`, `check_ai_injection`) — сломанный
  сканер не может тихо пройти;
* tamper-тесты: подмена tool-pin → drift, правка строки памяти → `tampered`,
  битый SHA фикстур (`learntoplay_source.json`, `map_gameplay.json`) → провал;
* негативные контролы физики (`test_warmup_physics.py --sanitize`);
* детерминизм-гейты (`build_* --check` — побайтовая свежесть генерируемых артов);
* покрытие C++ считается в CI (codecov).

Это не замена мутационному тестированию, но закрывает его главный сценарий
(«тест, который молчит при сломанной защите») для критичных контуров.

## 3. Какую нагрузку выдержит игра

**Железные потолки из кода (доказуемо):**

* **128 игроков на один процесс сервера** — `MAX_CLIENTS = SERVER_MAX_CLIENTS =
  128` (`src/engine/shared/protocol.h`); legacy-протокол — 64, vanilla — 16.
* Симуляция 50 тиков/с, `sv_mapupdaterate 15` для трансляции id 128 ↔ 64.
* Архитектура горизонтальная: N серверных процессов за master-листом; один
  бэкенд не в горячем пути матча (геймплей полностью сервер-авторитетен).

**Чего измерено нет:** ни одного нагрузочного прогона в репозитории. Практический
опыт апстрим-движка (64–80 игроков на публичных серверах) к этому коду применим
(движок тот же), но **не является замером этого проекта**. Рекомендуемый минимум
до открытого стресса: (1) прогон сервера с ботами/мульти-клиентным smoke на
32/64/128 слотов; (2) k6 на backend: `/api/ingest/solana` (rate-limiter,
idempotency), `/watchtower/events` (чтение), auth-эндпоинты; (3) SQLite WAL —
единственный писатель: потолок записи один поток, для beta-нагрузки достаточно,
для массового ingest нужен batch-режим или внешняя БД.

**Защитные ограничители уже в коде:** token-bucket `RateLimiter` на HTTP
(`backend/src/http.ts`, с фиксом обхода через поддельный X-Forwarded-For),
капы экономики (1000 intents на игрока/минт/эпоху по умолчанию), дедуп
телеметрии по нормализованному дайджесту.

**Остаточные риски (честно, из аудита и проверки):**
1. Hub-сторона Watchtower (внешний сервис) — вне репозитория; контракт для неё
   экспортируется, исполнение на ней.
2. Branch protection / отдельное подтверждение конфиг-изменений — настройка
   организации GitHub, не кода (77).
3. Kotlin-тесты ProgramPolicy написаны, исполняются в Android CI (Gradle здесь
   недоступен).
4. Мониторинг durable-nonce аккаунтов и сигнатур injection в живом трафике —
   операционная задача; точки съёма в API есть.

  для закрытия — §3.
