# Масштабирование до 4–5k CCU: архитектура и замеры

Документ отвечает на вопрос: 128 игроков на процесс — мало; что делать при
4 000–5 000 одновременных игроков. Все цифры получены реальными прогонами
`backend/scripts/load_test.ts` (v3) и `scripts/mutation_test.py` в этой ветке;
команды воспроизведения даны в конце.

## 1. Замеры (песочница, in-process приложение, SQLite `:memory:`, профиль smoke)

| Сценарий | Результат | Метки |
| --- | --- | --- |
| read (GET-профиль) | 32 702 запроса, 6 540 rps, p50 1.1 ms / p95 1.7 ms / p99 3.1 ms | 0 ошибок, 0 × 429 |
| ingest (burst + paced) | burst 10×50 = 500 событий принято (ровно окно лимитера), далее paced-фаза шеддится | 23.1% × 429 (по дизайну), p95 62 ms, 0 жёстких ошибок |
| flood (mixed write-shape) | 11 464 запроса, 1 721 rps | 24.9% × 429 — лимитер держит, 0 жёстких ошибок |
| mixed (чтения + инжест) | 20 731 запрос, 4 140 rps + 250 событий принято | без жёстких ошибок |

Ключевой вывод замеров: read-поверхность почти бесплатна (тысячи rps на один
процесс бэкенда), а ingest сознательно шеддится лимитером
(`RateLimiter(10, 5/60 000)` на `bucket:ip`, батч до 500 событий) — это защита,
а не деградация: 429-classified shedding не ломает клиентов, которые батчат и
ретраят. Устойчивый поток с одного IP — ~5 батч-запросов/мин × 500 событий
≈ 41 событие/s; серверные хосты шлют телеметрию агрегированно, игроки — только
через индексатор/батчи.

## 2. Арифметика процессов

Слоты на матчевый процесс — константа протокола: `MAX_CLIENTS = 128`
(`src/engine/shared/protocol.h`; legacy-сборка — 64, ванильный профиль — 16).

- 5 000 CCU / 128 слотов ≈ **40 процессов** при идеальной укладке;
- планировать нужно с запасом на неравномерность карт/режионов: **~50 процессов**;
- при плотности 64 слота (legacy-профиль) — 78 процессов.

Поднимать слоты «вверх» нельзя: это размеры протокольных структур и обмена
состоянием за тик (нагрузка растёт быстрее линейного от числа игроков в
процессе, тикрейт начинает падать). Масштабируем **числом процессов**, а не
слотами.

## 3. Архитектура

### 3.1 Игровой слой — флот матчевых процессов

- Флот stateless-от-запроса матчевых процессов (по 128 слотов) за
  master-листом/матчмейкингом; игрок получает адрес процесса после подбора
  матча, ретраи и реконнекты — на уровне сессий бэкенда.
- Регионы (EU / NA / CIS): свой пул процессов и, при необходимости, своя БД
  (шард по регионам — см. 3.3).
- Хостинг: 16-ядерный хост держит порядка 10–12 процессов (1 ядро + память под
  снапшоты на процесс, с запасом) ⇒ 5 000 CCU — это ~4–5 игровых хостов плюс
  резерв под деградацию/деплой. Процесс умирает по завершении матча —
  переупаковка без даунтайма.

### 3.2 Контрольный слой — бэкенд вне горячего пути матча

Матчевой трафик идёт напрямую клиент↔игровой процесс. Бэкенд (Hono) участвует
только в auth/сессиях/экономике/телеметрии/раздаче статики:

- stateless за балансировщиком, горизонтально масштабируется добавлением
  реплик; замер 6 540 rps чтений на один процесс показывает, что одному
  процессу хватает с большим запасом даже на пиковые 5k CCU (poll'ы, лобби,
  статусы) — но реплики нужны на отказоустойчивость, а не для rps;
- защита уже в коде: `limiter` (10/5-per-min) на мутации, `readLimiter`
  (60/60-per-min) на economy-чтения, `guardWith` → 429, ingest — bearer
  `sha256` + `timingSafeEqual`.

### 3.3 Данные — единственный писатель SQLite как узкое место

- Сейчас: SQLite (WAL, STRICT-таблицы), один писатель. Замеры показывают, что
  записи телеметрии, при батчинге и агрегации с хостов, не упираются в лимит
  даже на 5k (десятки событий/с, а не тысячи).
- Путь роста по шагам: (1) батч-коммиты и подготовленные выражения (уже есть),
  (2) шард по регионам — одна БД на регион, (3) при появлении
  межрегиональных запросов/аналитики — Postgres с read-replicas. Код
  изолирует SQL в `backend/src/db.ts` и стора (`sessions.ts`, `admin.ts`,
  `watchtower.ts`) — миграция не разносит приложение.

### 3.4 Телеметрия и Watchtower

- Клиенты/хосты шлют события батчами до 500 (`POST /api/ingest/solana`),
  индексатор цепи — тем же защищённым каналом; ingest-лимитер сознательно
  оставляет ~41 событие/s на IP — этого хватает агрегаторам, а мусорный поток
  отсекается 429 ещё до БД.
- При росте потока: очередь между ingest и писателем (in-process drain loop),
  агрегация счётчиков на игровых хостах (матчи, а не посекундные события) и
  шард записи по регионам (3.3).

### 3.5 Фронтенд

Статика (`design/`, `docs/`) — на CDN; единственный динамический контур — API
бэкенда. Отдача статики из процесса бэкенда допустима на старте, но не должна
съедать бюджет rps в проде.

## 4. Эксплуатация нагрузочных и мутационных тестов

```bash
# Нагрузка (нулевые зависимости, in-process):
cd backend
npm run load:smoke    # 5-секундный гейт для CI и локальных пробегов
npm run load          # стандартный профиль (20 c)
npm run load:soak     # 300-секундный пролив перед релизом
# Гибкое управление:
node --experimental-strip-types scripts/load_test.ts \
  --scenario mixed --profile standard --concurrency 32 --assert

# Мутационные тесты (7 модулей → их сьюты, 6 операторов):
python3 scripts/mutation_test.py --smoke            # быстрый гейт CI
python3 scripts/mutation_test.py                    # полный прогон
python3 scripts/mutation_test.py --module watchtower.ts --threshold 0.95
python3 scripts/mutation_test.py --list             # что будет мутироваться
```

Оба гейта проведены в `scripts/ci-local.sh` и в job «backend»
`.github/workflows/ci.yml` (load smoke + mutation smoke).

### Результаты мутационного прогона (полный, cap 25/модуль, seed 20260928)

| Модуль | Kill rate | Комментарий |
| --- | --- | --- |
| ai_guard.ts | 25/25 (100%) | включая позитивные проверки `containsInjectionVectors` |
| http.ts | 25/25 (100%) | роутер, лимит тела, bearer |
| sessions.ts | 7/7 (100%) | |
| crypto.ts | 14/15 (93%) | выживший — проверка целочисленности в парсере конфига (дублируется валидацией конфига) |
| watchtower.ts | 21/25 (84%) | выжившие: счётчик `unsigned` (косметика), guard идемпотентности миграции, два null-чека, которые дублирует STRICT-схема БД |
| tool_registry.ts | 9/10 (90%) | выживший — порядок сортировки канонического JSON (вывод детерминирован) |
| admin.ts | 20/25 (80%) | выжившие: лимиты усечения/итоги COUNT (косметика), half-config split-roles (дублируется валидацией конфига) |
| **Итого** | **121/132 (92%)** | порог гейта по умолчанию 0.90, цель — доматывать до 0.95 |

Реальные дыры, найденные мутационным прогоном и **закрытые тестами** в этой
ветке: инициализация `matched` в роутере, `match_id`/`session_id`/
`external_id`/`solana_wallet` в envelope-маппинге Watchtower, clamp
`reason` в админ-аудите, null-input `normalizeSolanaEvent`, границы
`parseProposalParams` (float/негатив/строки), `bearerToken` с массивными
заголовками, лимит тела 413, проверка дробного `occurred_at` (с пиннингом
сообщения — STRICT-схема дублирует проверку, иначе мутант эквивалентен).

Остаточные выжившие перечислены выше по классам: косметические лимиты,
идемпотентность миграции и поведение, которое уже закрыто валидацией конфига
или STRICT-схемой. Доматывать их стоит по мере появления тестов, которые пинят
конкретные сообщения/границы; порог в CI поднимать ступенями
(`--threshold 0.95` уже поддержан).

## 5. Чек-лист перед выходом на 5k

1. Замерить реальные матчевые процессы на целевом хосте (в песочнице собрать
   игровой сервер нельзя — нет cmake/ninja; сборка и замер тикрейта на
   продовом хосте).
2. Поднять пул процессов под ~50 одновременных матчей, включить master-лист.
3. Разнести БД по регионам; включить батч-коммиты телеметрии.
4. `npm run load:soak` и `python3 scripts/mutation_test.py` — зелёные.
5. CDN для статики, алерты на 429-долю ingest и на p95 auth.
